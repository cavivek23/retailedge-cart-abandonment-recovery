# RetailEdge Cart Abandonment Recovery Specification

## 1. Feature Overview

RetailEdge identifies carts that have had no customer activity for a configured
period, attempts recovery through a voucher and notification workflow, and
records the resulting customer, order, and campaign events for analytics.

The business objective is to recover incremental revenue without sending
duplicate or unauthorized messages, issuing invalid discounts, exposing data
across stores, or losing work when a scan fails part way through a batch.

The feature is store-scoped. A store operator can scan and inspect only that
store's carts and recovery records. A customer can inspect only their own
recovery record. Administrative analytics and scan operations require an admin
role and the corresponding scope.

The implementation must use the repository's layered architecture:

```text
ORM models and migrations -> repositories -> domain services -> FastAPI routes
                                             ^
                                  authentication dependencies
```

Services own business rules. Repositories own SQLAlchemy queries and
transactions. Routes own HTTP status codes and DTO binding. No service may use
raw SQL or a direct database driver.

## 2. Domain Models

All identifiers are opaque strings or UUIDs generated by the platform. They
must be canonicalized and validated at the boundary. All timestamps are UTC
and stored as timezone-aware database timestamps.

### 2.1 AbandonedCart

| Field | Type | Rules |
|---|---|---|
| `id` | UUID, primary key | Immutable resource identifier. |
| `store_id` | string, max 128 | Required tenant key; foreign key to the store authority when available. |
| `customer_id` | string, max 128 | Required customer identity; never accepted from an untrusted request body. |
| `status` | enum | `ABANDONED`, `RECOVERY_PENDING`, `RECOVERED`, `EXPIRED`, `CLOSED`. |
| `currency` | string, length 3 | Uppercase ISO 4217 code. |
| `subtotal` | `Decimal` / `NUMERIC(19,4)` | Non-negative monetary amount. |
| `discount_total` | `Decimal` / `NUMERIC(19,4)` | Non-negative monetary amount. |
| `tax_total` | `Decimal` / `NUMERIC(19,4)` | Non-negative monetary amount. |
| `total` | `Decimal` / `NUMERIC(19,4)` | Non-negative; computed from the authoritative pricing result. |
| `last_activity_at` | UTC datetime | Last customer/cart mutation used for abandonment eligibility. |
| `abandoned_at` | UTC datetime nullable | Set once when the cart first becomes eligible. |
| `recovered_at` | UTC datetime nullable | Set only after a qualifying order event. |
| `version` | positive integer | Optimistic concurrency version. |
| `created_at` | UTC datetime | Immutable creation time. |
| `updated_at` | UTC datetime | Updated on every state mutation. |

Relationships: one cart has many `CartItem` rows and zero or one current
`Recovery` row. A cart belongs to exactly one store and one customer.

| Field | Type | Rules |
|---|---|---|
| `id` | UUID, primary key | Immutable item identifier. |
| `cart_id` | UUID, foreign key | Required parent cart; delete behavior must be explicit in migrations. |
| `product_id` | string, max 128 | Product reference or immutable product snapshot reference. |
| `quantity` | `Decimal` / `NUMERIC(18,3)` | Positive; scale is at most 3 places. |
| `unit_price` | `Decimal` / `NUMERIC(19,4)` | Non-negative price at cart capture time. |
| `discount_total` | `Decimal` / `NUMERIC(19,4)` | Non-negative amount for this item. |
| `tax_total` | `Decimal` / `NUMERIC(19,4)` | Non-negative amount for this item. |
| `currency` | string, length 3 | Must equal the parent cart currency. |
| `created_at` | UTC datetime | Creation time. |

The recovery workflow uses item snapshots. It must not silently reprice a cart
using current catalog data.

### 2.4 Voucher

| Field | Type | Rules |
|---|---|---|
| `id` | UUID, primary key | Voucher identifier. |
| `recovery_id` | UUID, unique foreign key | Voucher belongs to one recovery. |
| `store_id` | string, max 128 | Tenant key. |
| `code_hash` | fixed-length binary/string | Store a hash, not the plaintext voucher code. |
| `code_last4` | string, length 4 nullable | Optional operational display value; not sufficient to redeem. |
| `discount_type` | enum | `PERCENT` or `FIXED_AMOUNT`. |
| `discount_value` | `Decimal` / `NUMERIC(19,4)` | Positive; percent is bounded to 0-100. |
| `currency` | string, length 3 nullable | Required for fixed amount; must equal cart currency. |
| `minimum_cart_total` | `Decimal` / `NUMERIC(19,4)` nullable | Non-negative and same currency when present. |
| `expires_at` | UTC datetime | Redemption deadline. |
| `redeemed_at` | UTC datetime nullable | Set by the order/voucher authority, not by analytics. |
| `created_at` | UTC datetime | Issuance time. |

Voucher issuance must be idempotent per `recovery_id`. The notification service
receives the plaintext code only through the approved secret-bearing provider
interface and it must never be logged.

## 3. Database Indexes and Constraints

All indexes are ORM declarations and must also be represented in migrations.

| Name | Columns and type | Query supported |
|---|---|---|
| `ix_cart_abandonment_scan` | B-tree `(store_id, status, last_activity_at, id)` | Find eligible abandoned carts for one store in stable cursor order. |
| `ix_recovery_store_status` | B-tree `(store_id, status, updated_at, id)` | Paginate recovery records and filter by workflow status. |
| `ix_recovery_customer_cart` | B-tree `(store_id, customer_id, cart_id)` | Authorize and retrieve a customer's recovery by cart. |
| `ix_analytics_store_time` | B-tree `(store_id, occurred_at, id)` | Paginate analytics events for a store and time range. |
| `uq_recovery_cart` | Unique B-tree `(cart_id)` | Prevent duplicate active recovery workflows. |
| `uq_analytics_event_key` | Unique B-tree `(event_key)` | Make inbound events idempotent. |

Required database constraints include non-negative monetary fields, positive
quantities, valid versions, valid status transitions where enforceable, and
matching currency between a cart and its items. Database constraints are
defense in depth; DTO and service validation remain mandatory.

## 4. Layered Service Responsibilities

### 4.1 AbandonmentScanService

Input: authenticated admin principal, `store_id` derived from that principal,
`batch_size`, optional opaque `cursor`, and the configured abandonment age.

Output: `processed_count`, `eligible_count`, `recovered_started_count`,
`failed_count`, `nextCursor`, and `hasMore`.

Rules:

1. Query only the authenticated store.
2. Select carts with `status=ABANDONED` or the configured eligible status and
   `last_activity_at <= now - abandonment_window`.
3. Order by `(last_activity_at, id)` and use an opaque cursor containing both
   values. Do not use offset pagination.
4. Process no more than `batchSize` records per batch.
5. Create or reuse the recovery idempotently, issue or reuse a voucher, and
   enqueue or send a notification through injected dependencies.
6. Commit each batch independently.
7. Advance the cursor only after the batch transaction and required downstream
   idempotency records succeed. On failure, retain the last successful cursor.
8. A restart with the same cursor must safely retry records without creating a
   second recovery, voucher, notification, or analytics event.
9. Emit sanitized audit and analytics events for each state transition.

### 4.2 RecoveryQueryService

Input: authenticated principal and `cart_id`.

Output: a response DTO containing recovery status, voucher status and expiry,
notification status, and recovery timestamps. It must not return voucher
plaintext, customer contact data, provider payloads, or internal ORM fields.

Rules:

- Require `store_id` ownership in the service even when the route has checked it.
- Customers may access only their own `customer_id`; store staff require an
  explicit read scope.
- Return the same not-found contract for an inaccessible resource where policy
  requires resource-existence hiding.

### 4.3 RecoveryAnalyticsService

Input: authenticated admin principal, bounded time range, optional event/status
filters, cursor, and limit.

Output: aggregate recovery metrics plus `nextCursor` and `hasMore`. Metrics
must identify the store and time window used without exposing customer-level
rows.

Rules:

- Admin role and `analytics:read` scope are mandatory.
- Queries are always store-scoped and bounded by a maximum time range and limit.
- Decimal amounts are aggregated as database numeric values and serialized as
  decimal strings or JSON numbers with an explicitly documented precision;
  Python float arithmetic is forbidden.
- Duplicate events are excluded by `event_key` idempotency.

## 5. API Specification

All endpoints use JSON and require a correlation ID. Error responses have this
shape:

```json
{"error": {"code": "machine_readable_code", "message": "safe message"}}
```

The API must not expose exception causes, SQL details, tokens, voucher codes,
or provider payloads.

### 5.1 POST `/scan/abandoned-carts`

Purpose: scan one authenticated store for eligible carts and start recovery.

Authorization: admin role plus `inventory:read` and `recovery:write` scopes.

Request DTO (extra fields forbidden):

```json
{
  "batchSize": 100,
  "cursor": "opaque-cursor-or-null"
}
```

`batchSize` is an integer from 1 through the configured maximum. `cursor` is
optional and must be an opaque cursor issued by RetailEdge for the same store
and scan policy. `store_id`, actor identity, and policy thresholds are not
accepted in the body.

Responses:

- `202 Accepted` when work is queued, or `200 OK` when the scan is synchronous;
  the deployment must choose one model and document it consistently.
- Body includes `processedCount`, `eligibleCount`, `startedCount`,
  `failedCount`, `nextCursor`, and `hasMore`.
- `401` for missing or invalid JWT claims.
- `403` for non-admin or missing scope.
- `422` for invalid batch size or cursor.
- `409` for a scan lease/conflict if only one scan may run per store.

### 5.2 GET `/carts/{id}/recovery`

Purpose: retrieve the recovery status for one cart.

Authorization: authenticated customer owner or authorized store staff with
`recovery:read`. The route must compare the path cart ID, authenticated
`store_id`, and authenticated `customer_id`/role before service access.

Response fields: `recoveryId`, `cartId`, `status`, `voucher` with type/value/
expiry but never plaintext code, `notificationStatus`, `recoveredAt`, and
`updatedAt`.

Responses: `200`, `401`, `403`, `404`, and `409` for a detected version or
workflow conflict.

### 5.3 GET `/analytics/recovery`

Purpose: return store-level recovery metrics.

Authorization: admin role plus `analytics:read`. Non-admin callers receive
`403` with a stable machine-readable code.

Query parameters:

- `from`: required UTC start timestamp.
- `to`: required UTC end timestamp, after `from` and within the configured
  maximum range.
- `status`: optional allowlisted recovery status.
- `cursor`: optional opaque cursor.
- `limit`: integer from 1 through 100, with a configured lower default.

Response:

```json
{
  "metrics": {
    "abandonedCount": 0,
    "recoveryStartedCount": 0,
    "recoveredCount": 0,
    "conversionRate": "0.0000",
    "recoveredAmount": "0.0000",
    "currency": "USD"
  },
  "nextCursor": null,
  "hasMore": false
}
```

The response must not include customer rows. Multi-currency results must be
grouped by currency or rejected; they must never be summed without an explicit
FX policy.

## 6. Pagination and Restartability

Every list or scan response uses `cursor`, `limit`, `nextCursor`, and
`hasMore`. Cursors are opaque, signed or integrity-protected, store-bound, and
encode the complete stable ordering key. The API never accepts `page`,
`offset`, or `skip`.

For scans, the cursor is the last successfully committed `(last_activity_at,
cart_id)` pair. Each batch has its own transaction and commit. A failure after
batch N must leave the checkpoint at batch N-1. Retrying from that checkpoint
is safe because recovery, voucher, notification, and analytics writes all use
idempotency keys.

`batchSize` is configurable through deployment configuration, with a positive
default and hard maximum. A scan must not load all eligible carts into memory.

## 7. Authentication and Authorization

JWT middleware must:

1. Pin verification to exactly the configured `RS256` or `HS256` algorithm.
2. Reject `alg=none`, algorithm mismatch, invalid signatures, and key confusion.
3. Require and validate `exp`, `iat`, and `nbf`; failures return HTTP 401 with
   distinct stable codes.
4. Extract and validate `store_id`, `customer_id`, `role`, and `scope`.
5. Apply bounded identifier validation and reject blank, oversized, or
   malformed claims.

`store_id` is always derived from the authenticated principal. It is never
trusted from a write body. Controllers compare path tenant values to the
principal, and services repeat the check for defense in depth.

Every resource-by-ID operation performs BOLA checks using both store ownership
and, where applicable, customer ownership. Admin-only operations return 403 to
non-admin tokens. Write DTOs use explicit allowlists and reject unknown fields;
ORM models are never bound directly to request bodies.

## 8. Validation and Edge Cases

- Cart abandonment uses UTC timestamps and a single configured threshold.
- A cart with no items, zero total, an invalid currency, or an already-created
  order is not eligible; exact behavior for zero-value carts is a product
  decision recorded below.
- A cart already in `RECOVERED`, `EXPIRED`, or `CLOSED` state is not rescanned.
- State transitions are validated and versioned; stale writes return HTTP 409.
- Quantities use `NUMERIC(18,3)` and monetary values use `NUMERIC(19,4)`.
  Values must be finite `Decimal` instances, never binary floats, and must not
  exceed the declared precision or scale.
- Currency is explicit on every monetary aggregate. Mixed currencies are not
  aggregated.
- Voucher percentages are 0-100; fixed discounts require matching currency;
  discounts cannot exceed the eligible cart total unless product policy says
  otherwise.
- Notification, voucher, order, and analytics retries are idempotent.
- Provider timeouts create a retryable failure state and do not advance the
  scan checkpoint until the workflow records a safe retry outcome.
- Malformed or expired cursors return 422 and do not fall back to an
  unbounded query.
- Missing resources and unauthorized resources use the documented 404/403
  policy consistently to avoid cross-tenant existence leaks.
- No log, event, metric, or error may contain credentials, JWTs, voucher
  plaintext, customer names, email addresses, addresses, or raw provider data.

## 9. External Dependencies

### Notification service

Input: template ID, locale, redacted customer reference resolved by the
provider, voucher delivery data, recovery ID, and idempotency key. It must
support timeout, retry, and provider-status polling without exposing customer
PII to logs.

### Voucher service

Input: store, recovery, currency, discount policy, expiry, and idempotency key.
Output: voucher ID, redacted display metadata, and secret delivery material
through the approved channel. Issuance must be atomic or safely compensatable.

### Order-event service

Consumes signed or authenticated order events containing order ID, cart ID,
store ID, customer ID, amount, currency, and event ID. It validates tenant and
customer ownership, deduplicates by event ID, marks recovery only after a
qualifying order, and emits `ORDER_RECOVERED` once.

### Analytics service

Consumes allowlisted, redacted `AnalyticsEvent` records using an idempotent
event key. Analytics failure must not cause a second voucher or notification;
the event may be retried from an outbox or retry queue.

All dependencies are injected behind interfaces and mocked in unit tests.

## 10. Testing Requirements

Tests must include:

- Valid and invalid JWT signatures, `alg=none`, algorithm confusion, and
  missing/expired/early `exp`, `iat`, and `nbf` claims.
- Cross-store and cross-customer resource access returning the documented
  403/404 result.
- Non-admin scan and analytics requests returning 403.
- Unknown DTO fields, invalid IDs, invalid cursor, invalid batch size, bad
  currency, float quantities, excess Decimal precision, and negative values.
- Negative-stock prevention at DTO, service, and database constraint levels.
- Concurrent/stale updates returning 409 without lost stock.
- Duplicate scan, voucher, notification, order, and analytics events.
- Independent batch commits and restart from the last successful cursor.
- Notification, voucher, order-event, and analytics timeout/failure behavior.
- Multi-currency analytics and cursor pagination with `nextCursor`/`hasMore`.
- No test output or structured log contains tokens, voucher codes, or customer
  PII.

## 11. Assumptions and Open Questions

The following decisions are required from the product team before implementation
is considered complete:

1. What is the default abandonment window, and can it vary by store?
2. Which cart statuses and activity types make a cart eligible?
3. Are zero-value carts, guest carts, and carts with unavailable products
   eligible for recovery?
4. Which roles may scan, issue vouchers, read customer recovery data, and read
   analytics? The baseline above reserves scans and analytics for admins.
5. What discount type, value, minimum spend, expiry, and stacking rules apply?
6. Is one recovery allowed per cart forever, or can a failed/expired cart be
   re-entered after a cooldown?
7. What event qualifies an order as recovered: payment authorization, capture,
   shipment, or another order state?
8. What are the notification channels, templates, locale rules, and opt-out
   requirements?
9. What maximum scan batch size, retry count, provider timeout, and scan lease
   duration are acceptable?
10. Should unauthorized resource access return 403 or deliberately look like
    404 to prevent resource-existence disclosure?
11. Which FX policy applies when a store has multiple currencies?
12. What retention, deletion, and customer privacy rules apply to carts,
    recovery records, vouchers, and analytics events?
13. Which authoritative services own stores, customers, products, vouchers,
    orders, and notification consent, and what are their availability/SLA
    guarantees?
